ソーシャルグラフは人の集合で、各人が友達 ID のリストを持ち、人の ID のハッシュで多くのサーバーに分割されます。ルックアップサービスは、ID をその人を持つサーバーに対応付けます。2 人のユーザー間の最短経路を見つけるには、友達リストをバッチで取得する幅優先探索を走らせ、人気の人をキャッシュして、探索がめったにディスクに届かないようにします。

これは [System Design Primer](https://github.com/donnemartin/system-design-primer) の問題の 1 つで、[ソーシャルグラフの解答](https://github.com/donnemartin/system-design-primer/blob/master/solutions/system_design/social_graph/README.md)はこのページと並べて読む価値があります。

## 要件

機能要件:

- ユーザーが別の人を検索し、2 人をつなぐ最短の友達の連なりを見る。
- 友達関係は相互で、重みがない。
- 友達の追加や削除は両側を更新する。

非機能要件:

- グラフは 1 台のマシンに収まらない。
- 可用性が高く、検索が即座に感じられるほど読み取りのレイテンシが低い。
- トラフィックは偏る。有名人と少数の人気の検索が大半を占めます。

## 負荷を見積もる

ユーザー 1 億人、1 人あたり友達 50 人、月に 10 億回の検索を想定します。

- エッジ: 100,000,000 x 50 で 50 億の有向エントリ、つまり 25 億の友達関係が 2 回保存されます。
- ストレージ: 友達 ID 1 つが 8 バイトなら、50 億エントリは ID で 40 GB です。プロフィールデータとインデックスを足しても数百 GB なので、限界はディスクではなく、メモリとクエリ率です。
- 検索率: 1,000,000,000 / 2,500,000 秒で毎秒約 400 回の検索です。
- 検索のコスト: 4 ホップの経路は、ホップごとに 50 人の友達へ広がります。3 ホップ目だけで 125,000 人、4 ホップ目では約 600 万人に届きます。1 回の検索が数百万の友達リストに触れることがあり、それが本当のコストです。

## 設計

### 人のシャーディング

人を `hash(person_id) mod N` で Person Server に分割します。ハッシュは負荷を均等に散らしますが、ID の範囲では新しいアカウントが最後のサーバーに積み上がります。[コンシステントハッシュ](/patterns/consistent-hashing)かシャードマップを使うと、サーバーを足しても動く人は一部だけです。[シャーディング](/patterns/sharding)を参照してください。

### ルックアップサービス

クライアントとグラフサービスは、どのサーバーがその人を持つかを知る必要があります。小さな Lookup Service がそのマップをメモリに保持してレプリケートし、クライアントはそれをキャッシュします。ハッシュなら、ルックアップは算術で、サービスは現在のシャードマップにすぎません。

### BFS による最短経路

1 台のマシンなら、始点から BFS を走らせ、目的の人が現れるまでレベルごとに友達へ広げます。シャードをまたぐ場合も User Graph Service は同じことをしますが、取得はバッチです。1 レベルのすべての ID を集め、シャードごとにまとめ、シャードごとに 1 つのリクエストを送ります。これで数百万の呼び出しが、レベルごとに数百に減ります。

より良い工夫は、両端から同時に探索し、2 つのフロンティアが出会ったところで止めることです。深さ 2 の探索を 2 つ行うと各々約 2,500 人に届きますが、深さ 4 の探索 1 つだと数百万人に届きます。

### キャッシュ

人気の人の友達リストは、多くの検索に現れます。Person Server の前に[キャッシュ](/components/cache)を置き、人気のペアの最近の BFS の結果を保持します。Facebook の TAO は、この考え方を大規模にしたものです。[グラフの前のキャッシュ](/patterns/cache-in-front-of-the-graph)を参照してください。

## 壊れるところ

**有名人。** 5,000 万人の友達を持つ 1 人は、経路のかなりの割合に入り、1 つのシャードへ読み取りの洪水を呼びます。その人のエントリをコピーにまたがって複製または分割し、1 回の検索が 1 つのノードから広げる友達の数に上限を設けます。[ホットキーとホットシャード](/patterns/hot-keys-and-hot-shards)を参照してください。

**長い経路。** 4 ~ 5 ホップ以内に経路が現れないなら、止めて「遠く離れている」と伝えます。上限のない BFS は、システムの残りより高くつくことがあります。

**シャード間のやり取り。** ホップごとに多くのサーバーに当たるので、テールレイテンシは最も遅いものが決めます。リクエストをバッチにし、タイムアウトを設定し、[ヘッジリクエスト](/patterns/hedged-requests)を検討します。

**リシャーディング。** サーバーを足すと人が動きます。[ID にシャードを入れる](/patterns/put-the-shard-in-the-id)のように、キーを人の ID に持たせれば、移動しても誰の番号も振り直されません。

## よくある質問

### ソーシャルネットワークで 2 人のユーザー間の最短経路を見つけるには。

始点から幅優先探索を走らせます。重みのないグラフで最短経路が見つかります。大きなグラフなら、両方のユーザーから同時に探索し、2 つの探索が出会ったところで止めます。そうすれば各側が進むのは数ホップだけです。

### ソーシャルグラフをシャードするには。

各人の ID をハッシュして、その人と友達リストを保存するサーバーを選びます。ルックアップサービスかシャードマップが、各 ID がどこにあるかをグラフサービスに伝えます。

### ソーシャルネットワークはグラフデータベースを使うべきですか。

Primer の演習は、それを使わず、シャード化したサーバーとルックアップサービスで行うよう求めています。Neo4j のようなグラフデータベースは小さめのグラフに向き、数十億のエッジでは、多くの企業がシャード化した MySQL 上の TAO のような専用のストアを作ります。

### System Design Primer はソーシャルグラフについて何と言っていますか。

問題を 2 人の間の最短経路の検索に絞り、人を Lookup Service の後ろの Person Server に分割します。このページはその形を保ち、バッチ化、双方向探索、有名人の問題を加えています。
