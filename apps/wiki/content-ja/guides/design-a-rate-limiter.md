レートリミッターは、クライアントごとにリクエストを数え、上限を超えたものを、たいていは HTTP 429 で拒否します。ゲートウェイで動かし、API キーか IP をキーにし、すべてのサーバーが同じ数を見られるようカウンターを Redis に置き、正確なウィンドウが要らないならトークンバケットを使います。難しいのは、アルゴリズムのバースト時の挙動と、共有カウンターを速く正しく保つことです。

この問題は、[System Design Primer](https://github.com/donnemartin/system-design-primer) の[追加の問題の一覧](https://github.com/donnemartin/system-design-primer#additional-system-design-interview-questions)にあり、そこに挙がっている参考文献は、レートリミッターについての Stripe の記事です。

## 要件

機能要件:

- クライアントごと、エンドポイントごとにリクエストを制限し、階層ごとに別のルールを持つ。
- 呼び出し側が上限を超えたら、Retry-After ヘッダー付きで 429 を返す。

非機能要件:

- すべてのリクエストの経路にあるので、リクエストに加える時間は 5 ms 未満にする。
- 多くのサーバーにまたがって動き、クライアントが 10 台のマシンに当たって上限の 10 倍を得られないようにする。
- フェイルオープンにする。リミッターのストアが落ちていたら、トラフィックは通す。

## 負荷を見積もる

アクティブなクライアントは 100 万、ピークは毎秒 50,000 リクエストで、それぞれ 1 回の確認が要るとします。

- スループット: 毎秒 50,000 回のカウンター操作です。Redis の 1 ノードは毎秒約 100,000 回の単純な操作をさばくので、1 ノードに収まり、レプリカが障害を受け持ちます。
- メモリ: トークンバケットにはトークン数とタイムスタンプが要り、キーを含めて約 50 バイトです。1,000,000 x 50 B は 50 MB です。
- スライディングウィンドウのログは、リクエストごとに 1 つのタイムスタンプを保存します。クライアントあたり毎分 100 リクエストなら、100 x 8 B x 1,000,000 で 800 MB です。10 倍です。

## 設計

確認は仕事の前に行うので、クライアントの身元が分かる限り早い位置に置きます。

### どこで適用するか

[APIゲートウェイ](/components/gw)なら、拒否されたリクエストは背後のサービスに何のコストも与えません。各サービス内のミドルウェアでも動きますが、拒否するリクエストに CPU を使います。クライアントごとの上限には身元が要るので認証のあとに置き、粗い IP ごとの上限はその前に置けます。

### アルゴリズム

| アルゴリズム                       | 挙動                                                         | コスト                                      |
| ---------------------------------- | ------------------------------------------------------------ | ------------------------------------------- |
| トークンバケット                   | 上限のレートで補充され、バケットの大きさまでのバーストを許す | クライアントごとに 2 つの数                 |
| リーキーバケット                   | 一定のレートで排出され、出力を滑らかにする                   | クライアントごとにキュー 1 つ               |
| 固定ウィンドウ                     | 毎分リセットされるカウンター                                 | ウィンドウの境目をまたぐと最大で上限の 2 倍 |
| スライディングウィンドウカウンター | 前のウィンドウを重なりで重み付けする                         | 2 つのカウンターで、ほぼ正確                |
| スライディングウィンドウログ       | すべてのタイムスタンプを保存する                             | 正確だが、メモリが最大                      |

Stripe と多くの公開 API はトークンバケットを使います。[レート制限](/patterns/rate-limiting)と[トークンバケット](/glossary/token-bucket)を参照してください。

### 共有カウンター

状態を Redis に置き、1 つのアトミックな Lua スクリプトで更新して、読み取り、補充、減算が割り込み合わないようにします。読んでから別々に書く 2 台のサーバーは、どちらも最後のリクエストを通してしまいます。各キーにウィンドウと同じ TTL を付けると、使われないクライアントは[キャッシュ](/components/cache)のようなストアから勝手に消えます。

## どこで壊れるか

**カウンターのストアがホットスポットになる。** 膨大なトラフィックのクライアント 1 つは 1 つのキーで、つまり 1 つのシャードです。各サーバーに小さなローカルの割り当てを持たせ、少しの超過を受け入れて、Redis とはバッチで同期します。[ホットキーとホットシャード](/patterns/hot-keys-and-hot-shards)を参照してください。

**制限されたクライアントがリトライして悪化させる。** 拒否されてすぐにリトライするクライアントは、負荷を足します。Retry-After を送り、[バックオフ付きリトライ](/patterns/retry-with-backoff)を求めます。[リトライストーム](/incidents/retry-storm)のインシデントがこのループを示します。

**上限が悪いユーザーと一緒に良いユーザーも止める。** 1 つの上限では、bot と買い物客を見分けられません。リミッターを [WAF とボット管理](/patterns/waf-and-bot-management)と組み合わせ、[ボット急増](/incidents/bot-surge)のインシデントも参照してください。サーバーが満杯のときは、[ロードシェディング](/patterns/load-shedding)が別の問いに答えます。誰が呼んでいるかではなく、どれだけ忙しいかです。

## Quorum で作る

最初の設計は、適用の地点です。レート制限付きの[APIゲートウェイ](/components/gw)をユーザーのあとに置き、[アプリサーバー](/components/server)と[データベース](/components/database)の前に立てます。アンロックには [APIゲートウェイ](/research/api-gateway)を、トークンバケットのバーストの選択肢を足すには[レート制限](/research/rate-limiting)をリサーチします。上限を超えると、ゲートウェイは `throttled` を返し、アプリサーバーはそのリクエストを見ません。キャプションのエラーは、容量ではなく上限から来ていることを確認してください。パターンは[レート制限](/patterns/rate-limiting)です。

::Design{id="gateway-rate-limit"}

2 つ目の設計は、別の問いに答えるもう 1 つの保護です。アプリサーバーはユーザーに対して小さすぎ、負荷のラインを超えると、価値の低いものから順に、リクエストの種別ごと拒否します。どの種別が速いままかを見てください。リミッターは誰が呼んでいるかを問い、シェディングはサーバーがどれだけ忙しいかを問います。[アプリサーバー](/components/server)と[データベース](/components/database)を使い、パターンは[ロードシェディング](/patterns/load-shedding)です。

::Design{id="shed-low-value"}

ゲームが扱うのは、1 か所でのアルゴリズムの選択、つまり 1 つのゲートウェイでの一定の上限かトークンバケットです。上限はクライアントごとではなくゲートウェイ全体で 1 つで、共有のカウンターストアもないので、クライアントごとのキーと分散カウントは紙の上のままです。[ボット急増](/incidents/bot-surge)のインシデントは、上限だけでは bot のフィルターにならない理由を示します。

## よくある質問

### どのレート制限アルゴリズムがいちばんよいですか?

ほとんどの API ではトークンバケットです。短いバーストを許し、クライアントごとに 2 つの数しか要らないからです。バーストの余地なしで滑らかでほぼ正確な上限が要るときは、スライディングウィンドウカウンターを使います。

### レートリミッターはどこで動かすべきですか?

APIゲートウェイかエッジで、サービスの前に置き、拒否されるリクエストが安く済むようにします。データベースや有料のサードパーティ API のような繊細なバックエンドの近くに、2 つ目の粗い上限を加えます。

### 複数のサーバーにまたがってレート制限するには?

カウンターを Redis のような共有の高速なストアに置き、スクリプトでアトミックに更新します。各サーバーがストアに問い合わせるので、すべてがクライアントごとに 1 つの数を見ます。

### レートリミッターが落ちたらどうなりますか?

ほとんどの API ではフェイルオープンにし、リミッターの障害がプロダクトの障害にならないようにします。バックストップとして、各サーバーに粗いローカルの上限を持たせます。
